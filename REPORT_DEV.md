Главная задача — сделать калькулятор максимально гибким, чтобы через настройки/админку можно было создавать разные сценарии расчёта без изменения frontend-кода.

### 1. Два основных сценария

Калькулятор должен поддерживать минимум два типа расчёта:

**Сценарий 1 — вся квартира**

Пользователь выбирает:
- всю квартиру;
- общую площадь квартиры;
- варианты/уровни отделки.

Стоимость считается по общей площади:

`площадь × цена за 1 м²`

При этом цена за м² может быть средней комплексной стоимостью ремонта квартиры и уже включать различные работы, в том числе ремонт отдельных помещений.

Например:

100 м² × 35 000 ₽ = 3 500 000 ₽.

Эту существующую логику не ломать.

**Сценарий 2 — отдельное помещение/зона**

Пользователь может выбрать не всю квартиру, а конкретное помещение или зону.

Например:
- ванная;
- кухня;
- спальня;
- гостиная;
- коридор;
- балкон;
- любое другое помещение.

Важно: список помещений НЕ должен быть жёстко прописан в коде.

Администратор должен иметь возможность добавлять, удалять и редактировать помещения через настройки.

### 2. Расчёт отдельного помещения

После выбора помещения пользователь должен указать его площадь.

Например:

«Площадь помещения»

`5 м²`

После этого пользователь выбирает варианты отделки, которые доступны для этого помещения.

Например для ванной:

- керамогранит;
- плитка;
- стены под покраску.

Для другого помещения набор вариантов может быть совершенно другим.

Нельзя делать условие вида:

`if room === "bathroom"`

или строить архитектуру вокруг ванной.

Всё должно работать через конфигурацию.

### 3. Варианты отделки должны быть динамическими

Каждый вариант отделки должен иметь собственную цену.

Например:

Помещение: Ванная

- Керамогранит — 60 000 ₽/м²
- Стены под покраску — 45 000 ₽/м²
- Плитка — 55 000 ₽/м²

Пользователь выбирает вариант, вводит площадь, и система считает:

`площадь × цена выбранного варианта`

Например:

5 м² × 60 000 ₽ = 300 000 ₽.

### 4. Возможность нескольких характеристик помещения

Калькулятор не должен предполагать, что для любого расчёта достаточно только площади.

Нужно заложить возможность в будущем создавать дополнительные вопросы.

Например:

Помещение:
→ площадь  
→ тип стен  
→ тип пола  
→ потолок  
→ дополнительные работы

Или:

Кухня:
→ площадь  
→ стены  
→ пол  
→ потолок

Или:

Балкон:
→ площадь  
→ утепление  
→ остекление  
→ отделка.

То есть администратор должен иметь возможность создавать последовательность вопросов/параметров для конкретного сценария.

### 5. Конфигурационная архитектура

Основная логика должна строиться примерно по принципу:

`Сценарий → Помещение → Вопросы → Варианты → Цена → Расчёт`

Не создавать отдельную программную логику для ванной, кухни, спальни и т.д.

Например, условная конфигурация:

```js
{
  type: "room",
  name: "Ванная",
  fields: [
    {
      type: "number",
      name: "area",
      label: "Площадь помещения",
      unit: "м²"
    },
    {
      type: "select",
      name: "wallFinish",
      label: "Отделка стен",
      options: [
        {
          name: "Керамогранит",
          price: 60000,
          unit: "m2"
        },
        {
          name: "Покраска",
          price: 45000,
          unit: "m2"
        }
      ]
    }
  ]
}
```

Это только пример архитектуры. Использовать существующую архитектуру проекта, если она уже позволяет решить задачу лучше.

### 6. Важно: не ограничиваться только одним вариантом отделки

Пользователь должен иметь возможность выбрать несколько характеристик ремонта, если они предусмотрены настройками.

Например:

Помещение 5 м²

Стены:
→ Керамогранит

Пол:
→ Керамогранит

Потолок:
→ Натяжной

Дополнительные работы:
→ Гидроизоляция

И итог должен складываться из всех выбранных параметров.

При этом для другого помещения набор параметров может быть совершенно другим.

### 7. Единицы расчёта

Не привязывать все цены только к м².

В конфигурации должна быть возможность указать единицу:

- м²;
- погонный метр;
- штука;
- комплект;
- фиксированная стоимость.

Например:

`1000 ₽/м²`

`2500 ₽/п.м.`

`15000 ₽/шт.`

`30000 ₽ фиксированно`

Это позволит в будущем использовать калькулятор не только для отделки.

### 8. Итоговый расчёт

После прохождения всех вопросов пользователь должен получать понятную разбивку:

Помещение:
`Ванная — 5 м²`

Отделка стен:
`Керамогранит — 300 000 ₽`

Отделка пола:
`Керамогранит — 100 000 ₽`

Потолок:
`Натяжной — 25 000 ₽`

Дополнительные работы:
`20 000 ₽`

**Итого: 445 000 ₽**

### 9. Админка

В админке должна быть возможность управлять конфигурацией калькулятора без изменения кода.

Минимально:

- создавать помещение;
- переименовывать помещение;
- удалять помещение;
- создавать вопросы;
- менять порядок вопросов;
- создавать варианты ответа;
- менять цены;
- менять единицу измерения;
- включать/выключать варианты;
- задавать формулу/тип расчёта;
- менять порядок отображения.

Например администратор добавляет:

«Балкон»

и самостоятельно создаёт:

Площадь → 1 500 ₽/м²  
Утепление → 2 000 ₽/м²  
Отделка → 3 500 ₽/м²

После этого новый сценарий должен работать без изменения frontend-кода.

### 10. Не ломать существующий калькулятор

Это обязательное требование.

Перед изменением необходимо изучить текущую реализацию:

- frontend калькулятора;
- backend;
- модели данных;
- настройки цен;
- существующие API;
- существующую админку;
- текущий механизм расчёта.

Существующий сценарий «Вся квартира» должен продолжить работать как раньше.

Нельзя просто переписать весь калькулятор ради новой функции.

Нужно встроить универсальную систему в существующую архитектуру с минимальными необходимыми изменениями.

### 11. Главное архитектурное требование

Не писать бизнес-логику вида:

```js
if (room === "bathroom") {
   ...
}

if (room === "kitchen") {
   ...
}

if (room === "bedroom") {
   ...
}
```

Помещение — это данные, а не отдельная программная логика.

Калькулятор должен понимать:

**что нужно спросить → какой вариант выбран → какая у него цена → как посчитать стоимость.**

А не понимать, что такое конкретно «ванная» или «кухня».

Цель — получить универсальный калькулятор ремонта, который в дальнейшем можно расширять через админку без постоянного внесения изменений в код.
